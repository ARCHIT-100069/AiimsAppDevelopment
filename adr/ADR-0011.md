# ADR 0011 — ORM selection: Prisma vs Drizzle for AIIMS+

**Status:** **Accepted** (confirmed by founders 2026-07-04) — Drizzle with the four mandatory guardrails · **Date:** 2026-07-03 · **Confidence:** Medium-High
**Phase classification (ADR 0010):** Structural Foundation — the ORM underpins the data layer, tenancy
enforcement (ADR 0002), and the FHIR facade (ADR 0003). Changing it later is expensive.
**Resolves:** Open Issues C-4.

## Context
We need one PostgreSQL data-access layer for a NestJS modular monolith whose two hardest, irreversible
requirements are (a) **RLS-enforced multi-tenancy** (ADR 0002) and (b) a **FHIR-R4-regenerable
relational model** (ADR 0003) — which in practice means heavy JSONB, polymorphic shapes, partial/GIN
indexes, and full-text search. Secondary constraints: long-term maintainability, team onboarding,
migration governance, complex analytical SQL, security, and enterprise durability. Our own principles
(ADR 0010) also value "boring, reliable technology when appropriate" and the founder rule *never merge
code you can't explain*.

The two credible candidates are **Prisma** and **Drizzle**. (TypeORM/Sequelize/Kysely were considered
and dropped: TypeORM/Sequelize are legacy-feeling with weaker TS ergonomics; Kysely is a query builder
without the schema/migration story we want as a foundation.)

## What each tool is
- **Prisma** — a *managed ORM*: its own schema DSL (`schema.prisma`), a generated type-safe client, and
  (historically) a query engine. Prisma 7 removed the Rust engine, improving performance and cold
  starts and simplifying deployment. Adds TypedSQL for type-safe raw SQL.
- **Drizzle** — a *SQL-first* library: schema defined in TypeScript, queries that read like SQL with
  full type safety, a thin runtime, and `drizzle-kit` for migrations. Exposes Postgres features
  (RLS policies, JSONB, custom types, indexes) declaratively in the schema.

## Criterion-by-criterion (weighted for AIIMS+)

| Criterion | Weight | Prisma | Drizzle | Edge |
|---|---|---|---|---|
| **Multi-tenancy / RLS** | ★★★★★ | RLS via session vars + Client Extensions; workable but bolt-on; helper libs (Yates, prisma-extension-rls). Policies live in manual migrations. | RLS is first-class: policies declared in-schema, versioned with the model. SQL-first makes per-tx session context natural. **Footgun:** drizzle-kit can drop/disable RLS policies if not told about them. | **Drizzle** (with guardrails) |
| **FHIR-compatible model** (JSONB, polymorphism, indexes, FTS) | ★★★★★ | Improving JSON support; less control over GIN/partial indexes and custom types; complex shapes fight the abstraction. | Direct control over JSONB, generated columns, partial/GIN indexes, `pg_trgm` search — maps cleanly to FHIR's irregular shapes. | **Drizzle** |
| **Complex / analytical SQL** | ★★★★ | TypedSQL helps; still more abstracted; some queries need raw escape hatches. | SQL-first; joins, CTEs, window functions expressed naturally with types. | **Drizzle** |
| **Long-term maintainability & onboarding** | ★★★★★ | Declarative schema + generated client = low cognitive load; **best-in-class docs and error messages**; easiest for new hires. | SQL-first demands stronger SQL fluency; docs improved but still behind Prisma; smaller (growing) talent pool. | **Prisma** |
| **Migrations & schema governance** | ★★★★ | `prisma migrate` is mature, predictable, well-tooled. | `drizzle-kit` is capable; **RLS-policy migration is the weak spot** (often hand-written; RFC open). | **Prisma** |
| **Performance & scalability** | ★★★ | Prisma 7 (engine-free) much faster than before; ample for our scale. | Thin layer, low overhead, fast cold starts (moot for long-lived Fargate). Proven at thousands of QPS with RLS. | Slight **Drizzle** |
| **Security posture** | ★★★★★ | Bolt-on RLS requires discipline; mature, no silent-drop behavior. | Native RLS is safer *by design*, but the silent-policy-drop footgun is a real hazard for PHI. | **Even** (both need the CI isolation gate from ADR 0002) |
| **NestJS integration** | ★★★ | First-class examples, common module patterns. | Integrates cleanly via providers; fewer canned examples. | Slight **Prisma** |
| **Ecosystem / durability / "boring"** | ★★★★ | Released 2021, very widely adopted, Prisma Studio, huge community — the lower-risk "boring" pick. | v1.0 stabilized out of beta only recently; adoption growing fast but younger. | **Prisma** |

**Tally of weighted edges:** the ★★★★★ criteria split — Drizzle wins the two that are *irreversible and
core* (RLS, FHIR model), Prisma wins the two that are *important but mitigable* (maintainability,
security-maturity). Prisma also wins most of the secondary criteria.

## The real decision
This is close and honest reasonable engineers differ. It comes down to a single trade:

- **Optimize for the two irreversible foundations (RLS + FHIR/Postgres control) and transparency →
  Drizzle.** These are exactly the things that are catastrophic to get wrong or retrofit, and Drizzle
  fits them natively. Its SQL-first nature also directly serves *"never merge code you can't explain"* —
  there's no hidden query engine; what you write is what runs.
- **Optimize for maturity, onboarding, docs, and "boring" → Prisma.** These matter for a decade-long,
  team-growing platform, and Prisma's weaknesses for our use case are workable rather than blocking.

## Recommendation
**Adopt Drizzle**, conditionally, with mandatory guardrails.

Reasoning: our two most expensive-to-reverse decisions (ADR 0002 RLS tenancy, ADR 0003 FHIR facade) are
precisely where Drizzle is natively strong and Prisma is historically weak. The requirement that PHI
isolation live *in the database, versioned with the schema* is served better by Drizzle's in-schema
policies than by Prisma's extension-based bolt-on. Drizzle's SQL transparency also aligns with the
founder's learning-first principle. Prisma's genuine advantages — docs, onboarding, migration maturity —
are real but **closeable with conventions and tooling**, whereas Prisma's RLS/JSONB gaps are structural
to how it abstracts the database.

### Mandatory guardrails (non-negotiable if we pick Drizzle)
1. **The cross-tenant isolation CI gate (ADR 0002) is the backstop** against the RLS silent-drop
   footgun — it fails the build if any tenant can read another's rows, regardless of tool behavior.
2. **RLS policies are managed as explicit, reviewed SQL migrations**, and drizzle-kit is configured to
   never manage/drop RLS unmanaged. Add a migration-diff check that alerts on any policy removal.
3. **Internal data-layer conventions doc + repository pattern** (ADR 0001) to compensate for thinner
   official docs and to keep query patterns consistent for new hires.
4. **Confirm Drizzle v1.0 stable status** at kickoff; if still pre-stable for our needs, revisit.

## When we would choose Prisma instead
- If we expect to hire junior/mixed-SQL-fluency engineers fast and prioritize onboarding speed over
  database-level control.
- If Drizzle v1.0 is not acceptably stable at Stage 0 kickoff.
- If we decide RLS-policy migration maturity outweighs native RLS ergonomics.
In that case Prisma 7 + a vetted RLS extension (Yates/prisma-extension-rls) + the same CI isolation
gate is a fully acceptable Plan B.

## Migration implications
- Decide **now** (Stage 0, before the first migration). Switching post-schema means rewriting schema
  definitions and query call-sites — weeks of rework plus regression risk on a PHI system.
- Our **repository / data-access layer** (ADR 0001) localizes ORM calls and reduces — but does not
  eliminate — lock-in. Do not let ORM types leak into domain or API layers; that keeps a future swap
  survivable.

## Verdict
**Drizzle, with the four guardrails above.** Confidence Medium-High. This is a foundational,
hard-to-reverse decision (ADR 0010 Structural Foundation), so it needs explicit co-founder confirmation
before Stage 0 migrations begin. If you prefer to optimize for onboarding/maturity over native
RLS/Postgres control, Prisma 7 is the sanctioned fallback and I'll switch the recommendation without
friction.
