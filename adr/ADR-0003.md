# ADR 0003 — Clinical data model: relational core + FHIR R4 facade

**Status:** Proposed · **Date:** 2026-07-03 · **Confidence:** High
**Reversibility: Very low — this shapes the core schema.**
**Phase classification (ADR 0010):** Structural Foundation — the FHIR-regenerable schema shape ships in
the MVP. Full FHIR mapping + NHA conformance is a Production Implementation; US Core / other profiles
are Future Enhancements.

## Context
ABDM requires health records to be shared as **HL7 FHIR R4 bundles (India profiles), encrypted, on
consent** (milestones M2/M3). Master Ch. 6 mandates a bespoke REST API and does not mention FHIR at
all — a gap, since FHIR is now a market-entry requirement, not a preference.

The tempting error is the opposite over-correction: making FHIR the primary transactional schema.
FHIR is deeply nested, verbose, and optimized for exchange, not for high-throughput OLTP or
developer velocity. Using it as the live store degrades query performance and slows every feature.

## Decision
**Relational core + FHIR facade.**

- The transactional store is a clean, normalized relational model (Patient, Encounter, Practitioner,
  Order, Observation, Condition, MedicationRequest, DiagnosticReport, …) designed for fast internal
  reads/writes and clear domain logic.
- The schema stores **enough fidelity to regenerate valid FHIR R4 India-profile resources** on demand.
- A dedicated **FHIR mapping layer** (in the ABDM adapter, ADR 0006) translates core → FHIR bundles at
  the interoperability boundary, and FHIR → core when ingesting as a Health Information User (M3).
- FHIR resource IDs and identifiers (incl. ABHA) are first-class in the core so mappings are stable.

## Consequences
- (+) Fast internal system, compliant external sharing — no compromise on either.
- (+) Insulates the domain model from FHIR spec/version churn (R4 → R4B → R5).
- (+) US Core / other national profiles later become additional mappings, not a re-modelling.
- (−) Mapping layer is real work and must be conformance-tested against ABDM/NHA validators.
- (−) Any clinical field ABDM requires but the core omits = a schema change; mitigate by reviewing the
  required FHIR India profiles up front and modelling to them.

## ORM implication
Because tenancy uses Postgres RLS (ADR 0002) and clinical queries get complex, evaluate **Drizzle**
(SQL-first, clean RLS/session-variable support) against Prisma before committing. Prisma is
acceptable only with reliable per-transaction session-GUC support and raw-SQL escape hatches.
Decision deferred to an implementation ADR, but flagged here because RLS + FHIR mapping are the
stress tests that should decide it.

## Alternatives considered
- **FHIR-native store (e.g. HAPI FHIR JPA as system of record):** rejected as the primary OLTP store;
  may still be used as a *read/exchange* projection if needed later.
- **Bespoke schema, map to FHIR ad hoc per integration:** rejected — leads to inconsistent, unstable
  mappings and repeated rework.
