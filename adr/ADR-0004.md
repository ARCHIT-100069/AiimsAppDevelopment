# ADR 0004 — Consent Architecture: Unified Consent Service with Progressive Integration

**Status:** Proposed · **Date:** 2026-07-03 · **Confidence:** High
**Phase classification (ADR 0010):** Structural Foundation (unified consent model + enforcement hooks)
+ MVP Implementation (mock adapters behind the interface). Real ABDM and DPDP Consent Manager
integrations are Production Integrations; consent analytics is a Future Enhancement.

## Context
The platform must eventually satisfy **two distinct consent regimes** without the core architecture
being coupled to either one from day one:

1. **Data-sharing consent** (ABDM-style) — time-bound, purpose-specific consent artifacts governing the
   **sharing** of health records between providers. Specifies HI types, date range, purpose
   (self-use / treatment / payment / research), and validity window.
2. **Data-processing consent** (DPDP Act 2023 / Rules 2025) — the lawful basis for **processing**
   personal data, with registered Consent Managers as intermediaries (registration operative from
   ~Nov 2026), plus notice, withdrawal, and grievance mechanisms.

Key design intent: **AIIMS+ must not appear or be architecturally dependent on ABDM to function.**
ABDM is one *integration* of a general consent capability, not the foundation of it.

## Decision
Build a **single Unified Consent Service** whose *domain model is regime-agnostic*, with real external
consent systems attached progressively behind stable interfaces.

### Structural Foundation (MVP — non-deferrable)
- A generic **consent artifact model**: subject, purpose, scope (HI types / resources), grant &
  withdraw events, validity window, provenance, version — expressed in AIIMS+'s own vocabulary, not
  ABDM's or any single regulator's.
- **In-code enforcement hooks**: no data is shared or processed without a valid, unexpired consent
  record resolved through the Consent Service. Enforced in code, not policy prose.
- **Adapter interfaces** for external consent authorities (a `ConsentProvider` port), plus withdrawal
  propagation via the event/outbox backbone (ADR 0005).
- **Feature flags** selecting which provider implementation is active per environment/tenant.

### MVP Implementation
- **Mock consent providers** behind the adapter interface: a stubbed data-sharing consent authority and
  a stubbed processing-consent flow that issue and validate artifacts locally. This makes the full
  "share-on-consent" and "consent-to-process" experience demoable end-to-end with **no external
  dependency**.
- A basic consent UI/UX (capture, view, withdraw) driving the demo.

### Production Integration (deferred behind the seam)
- Real **ABDM** consent-artifact exchange with the ABDM Consent Manager / gateway (data-sharing regime),
  wired through the ABDM adapter (ADR 0006).
- Real **DPDP** Consent Manager integration, notice/version management, and statutory withdrawal &
  grievance workflows.
- Swap is a configuration change (feature flag + provider implementation), not a re-architecture.

## Consequences
- (+) One coherent, auditable place to prove why any data flow was lawful — independent of vendor.
- (+) The product runs and demos fully without ABDM; ABDM/DPDP become progressive integrations.
- (+) ABDM and DPDP share machinery instead of diverging.
- (−) The generic model must be rich enough to map cleanly onto both regimes; validate the mapping when
  wiring each real provider.
- (−) Must track evolving Consent Manager interfaces (DPDP Rules staged through 2027).

## Non-negotiable
No PHI is shared to another provider without a valid, unexpired data-sharing consent artifact; no
processing occurs without a valid processing-consent lawful basis. True in MVP (mock) and Production
(real) alike — only the provider implementation changes.
