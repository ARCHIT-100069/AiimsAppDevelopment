# ADR 0005 — Audit: append-only, tamper-evident event log

**Status:** Proposed · **Date:** 2026-07-03 · **Confidence:** High
**Phase classification (ADR 0010):** Structural Foundation — the outbox + append-only hash-chained log
ship in the MVP. WORM/S3 Object Lock storage and the scheduled integrity verifier are Production
Implementations; SIEM integration is Future.

## Context
Audit is mandated three times over: the AIIMS+ Constitution (Master Ch. 19), the DPDP Act's
accountability and breach-reporting duties, and ABDM. "Audit logging" in Ch. 6 is listed as a
security feature — too weak. For healthcare it must be a **tamper-evident system of record**.

## Decision
An **append-only, hash-chained audit log**, written from day one:
- Every security- and PHI-relevant action emits an audit event via the transactional **outbox**
  (same backbone as ADR 0001), guaranteeing the audit write commits atomically with the business
  change.
- Events are **hash-chained** (each record includes the hash of the prior record) so any deletion or
  edit is detectable.
- Persisted to **WORM storage** (S3 Object Lock, compliance mode) for immutability and retention.
- Captures: who (user + tenant + role), what, which resource, when, source, consent basis (link to
  ADR 0004), and outcome.
- Audit data is read-only to the application; no update/delete paths exist.

## Consequences
- (+) Provable integrity for regulators, breach investigations, and internal forensics.
- (+) Uniform capture via the outbox — no reliance on developers remembering to log.
- (−) Volume: PHI-access auditing is high-cardinality; budget storage and partition/rotate WORM
  objects. Consider separating hot (queryable) from cold (immutable archive) tiers.
- (−) Hash-chain verification tooling must exist and be run (scheduled integrity check).

## Alternatives considered
- **Application `logger.info` audit:** rejected — mutable, gappy, non-provable.
- **CloudTrail/DB audit only:** necessary for infra, insufficient for application/PHI semantics.
