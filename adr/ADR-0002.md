# ADR 0002 — Multi-tenancy: Postgres RLS, promotable to dedicated DB

**Status:** Proposed · **Date:** 2026-07-03 · **Confidence:** High
**Reversibility: Very low — this must be decided before the first table is created.**
**Phase classification (ADR 0010):** Structural Foundation — `tenant_id` + RLS ship in the MVP and are
non-deferrable. DB-per-tenant promotion is a Production Implementation; automated provisioning is Future.

## Context
Master Ch. 6 states tenants must be "isolated securely while sharing resources efficiently" and
stops there. For a PHI platform this is the single most consequential architectural decision: it
drives compliance blast radius, per-tenant cost, data-residency options, and migration pain. It
cannot be retrofitted cheaply.

## Decision
**Row-Level Security (RLS) by default, with promotion to a dedicated database for large/sensitive
tenants.**

- Every tenant-scoped table carries a non-null `tenant_id`.
- Isolation is enforced by **PostgreSQL RLS policies at the database layer** — the application sets
  the tenant context per transaction; the DB, not app code, guarantees no cross-tenant read/write.
- A tenant can be **promoted** to a dedicated database (or dedicated cluster) without application
  changes — tenant isolation is a deployment/routing property, resolved by a tenant registry that
  maps tenant → connection.
- Connection routing and the RLS session variable are set in one place (a tenant-context middleware),
  never scattered.

## Consequences
- (+) Cheap, dense multi-tenancy for the long tail of clinics; strong isolation available on demand
  for large hospitals, regulated tenants, or data-residency-restricted customers.
- (+) DB-enforced isolation defends against the classic "forgot the `WHERE tenant_id`" leak.
- (−) Every connection path must set tenant context correctly; a missed path is a breach. Mitigate
  with a mandatory data-access layer, default-deny RLS, and automated tests that assert isolation.
- (−) RLS interacts poorly with some ORMs (see ADR 0003 / ORM choice) — the data layer must support
  setting session GUCs per transaction.

## Alternatives considered
- **Schema-per-tenant:** painful migrations at thousands of tenants; rejected as default.
- **Database-per-tenant for everyone:** too costly/operationally heavy for small clinics; kept only
  as the promotion target.
- **App-layer filtering only (no RLS):** rejected — one bug leaks PHI across tenants.

## Verification requirement
Ship an automated cross-tenant isolation test suite (attempt to read tenant B's rows under tenant A's
context; must fail) as a permanent CI gate.
