# ADR 0010 — Engineering principle: "Build the architecture once. Integrate progressively."

**Status:** Accepted (permanent engineering rule) · **Date:** 2026-07-03 · **Confidence:** High

## Context
AIIMS+ Phase 1 is a production-quality **prototype** to demonstrate the full product experience to
hospitals, investors, and early partners — not a legally live healthcare platform on day one. We need
a rule that prevents two opposite failures: (a) over-engineering regulatory/operational machinery that
is only required at go-live, and (b) skipping structural foundations that are cheap now but a rewrite
later — which would quietly make the prototype un-productionizable.

## Decision — permanent rule
> **Build the architecture once. Integrate progressively.**

Structural foundations that are difficult or expensive to retrofit are built from the start and are
part of the MVP. External integrations, certifications, regulatory onboarding, government connectivity,
hospital onboarding, payment/notification providers, and other operational infrastructure are
implemented **behind stable interfaces** using mocks, stubs, adapters, or feature flags until we are
production-ready.

The distinction is **structure vs integration**: mock the integrations, keep the structure.

### Structural foundations that MUST exist in the MVP
Tenant isolation · modular architecture · audit logging · event/outbox pattern · security boundaries ·
authorization model · API contracts · FHIR-compatible domain model · feature-flag framework ·
adapter interfaces.

## The four-way classification (apply to every future recommendation)
Every recommendation, module, and task is tagged with exactly one primary class:

1. **Structural Foundation** — must exist in the MVP because it is expensive/impossible to retrofit.
   Examples: `tenant_id`+RLS, audit outbox, FHIR-regenerable schema, consent artifact shape,
   per-record encryption keys, adapter interfaces, feature-flag framework.
2. **MVP Implementation** — real, working code needed to demonstrate the product experience now.
   Examples: patient registration, encounter/EMR core, basic Keycloak login, mock ABDM gateway.
3. **Production Implementation** — required for legal go-live; deferred behind a seam and mocked in
   MVP. Examples: real ABDM M1–M4 certification, DPDP Consent Manager wiring, WORM audit storage,
   live payment gateway, MFA/SSO, cross-region DR, retention/crypto-shred engine.
4. **Future Enhancement** — valuable later; not required for MVP or first production go-live.
   Examples: NHCX claims (M4), multi-country regions, US Core profiles, SIEM/analytics.

## Consequences
- (+) Prevents both over- and under-engineering with a single, testable question per item.
- (+) Guarantees the prototype is a strict subset of the production architecture, never a detour.
- (−) Requires discipline: a "Structural Foundation" item cannot be dropped for speed, even in the
  prototype. That is the point.

## Enforcement
- Every ADR carries a **Phase classification** line.
- Every roadmap item and non-trivial task carries one of the four tags.
- Code review rejects new external integrations that are not behind an adapter interface + feature flag.
