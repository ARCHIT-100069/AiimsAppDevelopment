# APDR-0002 — URI major versioning + additive-change + deprecation policy

**Status:** Accepted · **Version:** 1.0 · **Owner:** API/Backend Lead · **Date:** 2026-07-04

## Context
Partners and hospital integrations need a stable, unambiguous versioning contract and a predictable
deprecation path.

## Decision
**URI major version** (`/v1/…`). **Additive, backward-compatible** changes within a major version; never
remove/rename/repurpose a field in place. Breaking changes ⇒ new major version. Deprecations via
**`Deprecation` + `Sunset` headers** with a minimum support window and usage monitoring before removal.

## Alternatives Considered
- **Header/media-type versioning** — less visible/cacheable for partners. Rejected as primary.
- **No versioning / continuous breaking** — breaks integrations. Rejected.

## Trade-offs
URI versioning can fork routes at a major bump; clear and partner-friendly, worth it.

## Consequences
Stable integrations; safe evolution; no silent breakage.
