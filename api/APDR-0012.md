# APDR-0012 — FHIR API boundary separation (`/fhir/R4`)

**Status:** Accepted · **Version:** 1.0 · **Owner:** API/Backend Lead · **Date:** 2026-07-04

## Context
ABDM requires FHIR R4 (India profiles) exchange, but FHIR is verbose and interoperability-shaped — unfit as
the internal OLTP/API model (ADR 0003). It must not pollute the general REST surface.

## Decision
Serve FHIR **only** at `/fhir/R4/…`, owned by the **ABDM adapter** (mock in MVP), **regenerated** from the
relational model (ADR 0003). Consent-gated (ADR 0004), encrypted (SDR-0004). The internal REST API stays the
primary developer surface; the two evolve independently (FHIR versioned by the spec).

## Alternatives Considered
- **FHIR as the general API model** — verbose, slow, couples internal clients to the spec. Rejected.
- **No FHIR boundary** — fails ABDM interoperability. Rejected.

## Trade-offs
Two API shapes (REST + FHIR) and a mapping layer; buys fast internal API + compliant external exchange.

## Consequences
Clean separation; ABDM-conformant FHIR without burdening internal consumers.

## Dependencies
ADR 0003/0006, ADR 0004, SDR-0004.

## Confidence
High. ## Reversibility Low.

## Phase Classification
Structural Foundation (boundary) + Production Implementation (real ABDM FHIR).

## Related Documents

## Review Trigger
