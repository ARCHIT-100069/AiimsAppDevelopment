# APDR-0011 — Internal/external + public/private segmentation + gateway strategy

**Status:** Accepted · **Version:** 1.0 · **Owner:** API/Backend Lead · **Date:** 2026-07-04

## Context
Endpoints differ in exposure and trust; and we must decide whether to add a separate API-gateway product now
(ADR 0001 favors operational simplicity).

## Decision
- **External** (partner/tenant): versioned `/v1`, contract-governed, rate-limited, documented.
  **Internal** (service/BFF/admin): network-restricted, unpublished. Adapters/AI via internal ports only.
- **Private (authenticated, tenant-scoped)** is the default; **public (unauth)** is minimal (health, later
  status/marketing) with **no PHI**. Admin = private + elevated + audited.
- **Gateway:** ALB + WAF at the edge (Blueprint §17); gateway concerns (auth/tenant/authz/rate/validation/
  error) are the NestJS middleware pipeline. **No separate API-gateway product in MVP;** a managed
  partner/developer gateway (API keys) is Production/Future.

## Alternatives Considered
- **Dedicated API-gateway product now (Kong/APIGW)** — premature ops for MVP (ADR 0001). Deferred.
- **One flat surface for all consumers** — mixes trust levels. Rejected (segmentation).

## Trade-offs
Middleware-as-gateway keeps ops simple but centralizes concerns in the app; acceptable at MVP scale.

## Consequences
Clear exposure boundaries; simple edge; clean path to a managed gateway later.

## Dependencies
