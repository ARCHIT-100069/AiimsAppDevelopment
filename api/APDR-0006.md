# APDR-0006 — Idempotency-Key + optimistic concurrency

**Status:** Accepted · **Version:** 1.0 · **Owner:** API/Backend Lead · **Date:** 2026-07-04

## Context
Network retries must not create duplicate clinical/billing records, and concurrent edits must not silently
overwrite (DDR 0009, BDR 0004).

## Decision
**`Idempotency-Key` header required on unsafe POSTs** (create patient/order, payment intent); key + tenant +
endpoint persisted, replay returns the original result. PUT/PATCH/DELETE are idempotent; **optimistic
concurrency** via `If-Match`/version → **409** on conflict.

## Alternatives Considered
- **No idempotency** — duplicate records on retry. Rejected (safety).
- **Server-generated dedup only** — clients can't safely retry a create. Rejected.

## Trade-offs
Clients must send/keep keys; idempotency store adds writes. Essential for a clinical/billing API.

## Consequences
Safe retries; no duplicates; no lost updates.

## Dependencies
BDR-0004, DDR 0009, APDR-0003.

## Confidence
High. ## Reversibility Medium.
