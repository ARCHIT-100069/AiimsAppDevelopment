# SDR-0007 — Audit integrity & tamper-evidence

**Status:** Accepted · **Version:** 1.0 · **Owner:** Security Architect · **Date:** 2026-07-04

## Context
Audit must be provably intact for DPDP accountability, ABDM, and the Constitution — and resistant to
insider tampering.

## Decision
Append-only, **hash-chained** audit (DDR 0007) fed by the transactional outbox; `UPDATE`/`DELETE` revoked
from `aiims_app`; **WORM** archival (S3 Object Lock, compliance mode) in Production; scheduled **chain-
integrity verifier**. Captures actor/tenant/action/resource/consent-basis/outcome — **no PHI payloads**.
Access to audit is itself audited and least-privilege.

## Alternatives Considered
- Mutable audit table — not tamper-evident. Rejected.
- External SIEM as system of record — added as a sink (prod), not the primary integrity store.
- Blockchain ledger — overkill; hash-chain + WORM suffices.

## Trade-offs
Hash-chaining adds insert compute; WORM adds storage lifecycle. Mandatory for integrity.

## Consequences
Tampering is detectable; strong non-repudiation; compliance-ready.

## Dependencies
DDR 0007, SDR-0010 (logging), §15.

## Confidence
High.

## Reversibility
Low.

## Phase Classification
Structural Foundation (chain/outbox) + Production Implementation (WORM, verifier, SIEM).
