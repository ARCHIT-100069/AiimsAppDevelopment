# SDR-0005 — Key management: KMS CMK hierarchy + envelope + per-tenant CMK

**Status:** Accepted · **Version:** 1.0 · **Owner:** Security Architect · **Date:** 2026-07-04

## Context
Field encryption (SDR-0004) and at-rest encryption need a key hierarchy that isolates blast radius, rotates
cleanly, and enables tenant-level crypto-shred.

## Decision
- **AWS KMS** with **separate CMKs** for DB storage, S3, secrets, and PHI field-data keys.
- **Envelope encryption:** `GenerateDataKey` → per-record data keys wrapped by the PHI CMK; plaintext keys
  in memory only; `enc_key_ref` on the row.
- **Rotation:** automatic annual CMK rotation; key-policy-scoped grants; re-wrap on rotation.
- **Per-tenant CMK** for dedicated/high-sensitivity tenants (Production) → tenant-level shred.
- **No standing human access** to the production PHI CMK.

## Alternatives Considered
- Single CMK for everything — one compromise/rotation affects all data. Rejected.
- Self-managed keys/HSM now — operational burden; KMS suffices with a path to CloudHSM later.

## Trade-offs
Multiple CMKs add key-management overhead; envelope adds a wrap/unwrap step. Justified for isolation/shred.

## Consequences
Blast-radius isolation; crypto-shred feasible per record and (prod) per tenant; auditable key use.

## Dependencies
SDR-0004, DDR-0006, ADR-0007 (regional KMS), SDR-0012 (IAM).

## Confidence
High.

## Reversibility
Medium — re-keying is possible but costly; hierarchy choice is durable.

## Phase Classification
Structural Foundation (hierarchy + envelope) + Production Implementation (per-tenant CMK, CloudHSM option).

## Related Documents
SECURITY-BLUEPRINT §11, DDR-0006.

## Review Trigger
Key compromise; crypto-agility/algorithm upgrade; dedicated-tenant onboarding.
