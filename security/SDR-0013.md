# SDR-0013 — Incident response & breach notification

**Status:** Accepted (notification timelines legal-deferred) · **Version:** 1.0 · **Owner:** Security Architect
**Date:** 2026-07-04

## Context
A PHI platform must detect, contain, and lawfully report incidents. DPDP imposes breach-notification duties
(exact timelines to be legally confirmed).

## Decision
- **IR process:** detect → triage → contain → eradicate → recover → post-mortem, with defined severities and
  on-call.
- **Containment levers:** revoke tokens/keys, isolate a tenant/service, rotate secrets, disable feature flags.
- **Forensics** on immutable audit + logs; preserve evidence.
- **Breach notification:** notify the **DPDP Data Protection Board and affected data principals** within the
  DPDP-mandated window; design assumes prompt notification + a detailed follow-up report.
- Runbooks versioned in `/operations/` (Ops phase).

## Alternatives Considered
- Ad hoc response — slow, inconsistent, non-compliant. Rejected.
- Fixed hard-coded notification hours now — unverified; deferred to counsel to avoid asserting a wrong number.

## Trade-offs
Formal IR needs maintained runbooks and drills; essential for compliance and trust.

## Consequences
Faster, lawful, auditable incident handling; regulator-ready notification path.

## Dependencies
