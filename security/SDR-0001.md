# SDR-0001 — Identity & token architecture (Keycloak/OIDC/PKCE/BFF)

**Status:** Accepted · **Version:** 1.0 · **Owner:** Security Architect · **Date:** 2026-07-04

## Context
AIIMS+ needs strong, standards-based authentication for clinicians, staff, and services without building
identity (ADR 0008 chose Keycloak). Browser token handling for a PHI app must resist XSS/token theft.

## Decision
- Keycloak as OIDC provider; **Authorization Code + PKCE**; **BFF** (Next.js server) holds tokens in an
  httpOnly/Secure/SameSite cookie session — no tokens in the browser.
- Short-lived JWT access tokens (minutes) + rotating refresh tokens with reuse detection; tenant/org/role
  claims. Machine-to-machine via scoped client-credentials.
- Signatures/claims (`iss`,`aud`,`exp`,tenant) validated on every request against Keycloak JWKS.
- MFA (TOTP/WebAuthn) and hospital SSO federation = **Production** (hooks in MVP).

## Alternatives Considered
- SPA holding tokens in localStorage — XSS-exfiltration risk. Rejected.
- Build custom auth — liability, out of scope (ADR 0008). Rejected.
- Opaque tokens + introspection everywhere — extra latency; JWT + JWKS chosen, revocation via refresh rotation.

## Trade-offs
BFF adds a server hop and session plumbing; short tokens add refresh traffic. Both are correct for PHI.

## Consequences
No long-lived browser secrets; centralized revocation; clean path to MFA/SSO.

## Dependencies
ADR 0008 (Keycloak), Blueprint §8/§11, SDR-0008 (network TLS).

## Confidence
High.

## Reversibility
Medium — OIDC abstraction eases IdP change; token model swap is more involved.

## Phase Classification
Structural Foundation (OIDC/BFF/token model) + Production Implementation (MFA/SSO).

## Related Documents
ADR-0008, SECURITY-BLUEPRINT §4/§8.

## Review Trigger
New auth threat class; IdP change; MFA/SSO activation.
