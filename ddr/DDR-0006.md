# DDR 0006 — PHI encryption: identifiers-only field encryption + blind index + KMS envelope

**Status:** **Frozen — ratified by SDR-0004 (Phase 3, 2026-07-04)** · **Date:** 2026-07-04 · **Confidence:** High
**Implements:** ADR 0009 · **Ratified by:** SDR-0004

## Context
ADR 0009 requires crypto-shred readiness (per-record keys) so erasure can be honored by destroying keys.
Encrypting *all* clinical data would destroy queryability, indexing, and search.

## Decision
- **Field-encrypt direct identifiers only** — `abha_number`, `phone`, `email`, Aadhaar refs — via
  **envelope encryption**: a per-record/per-subject data key (AWS KMS `GenerateDataKey`) wrapped by a CMK;
  `enc_key_ref` stored on the row. Destroying the data key crypto-shreds the record.
- **Exact-match lookups** on encrypted identifiers use a **blind index** (keyed HMAC in `*_bidx`), so we
  never decrypt at query time.
- **All other columns** rely on Aurora at-rest KMS encryption + RLS and stay queryable/indexable.
- MVP ships the columns/helpers (Structural Foundation); the retention/shred engine + legal durations are
  Production (ADR 0009).

## Alternatives considered
- **Encrypt all PHI columns** — breaks search/joins/indexes; unusable OLTP. Rejected.
- **Transparent at-rest only (no field encryption)** — cannot crypto-shred a single subject. Insufficient
  for erasure rights.
- **`pgcrypto` in-DB with a DB-held key** — key lives next to data; weaker separation than KMS envelope.
  Rejected.

## Trade-offs
Encrypted identifiers need blind indexes for lookup and cannot be range-queried; acceptable for direct
identifiers. Balances DPDP erasure/crypto-shred against the blueprint's performance goals.

## Consequences
Flagged for **Security-phase sign-off** (DATABASE-ARCHITECTURE §19). Consistent with the frozen core; not
an architecture change.
