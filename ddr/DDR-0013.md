# DDR 0013 — Soft-delete, retention metadata & clinical versioning

**Status:** Accepted (durations deferred) · **Date:** 2026-07-04 · **Confidence:** Med-High
**Implements:** ADR 0009

## Context
DPDP erasure rights collide with medical-record retention law (ADR 0009). Clinical records also require an
amendment history for medico-legal reasons — they cannot be silently overwritten.

## Decision
- **Soft delete:** nullable `deleted_at`; default reads exclude soft-deleted rows via repository
  convention. Hard delete only through the retention engine (Production).
- **Retention metadata:** `retention_class`, `retention_until` per record — **fields ship now**, values
  set once legal durations are validated (ADR 0009).
- **Clinical amendments are versioned:** an amendment writes a new version (`status = amended`) and
  preserves prior versions; MVP uses in-row `version` + full audit trail, dedicated history tables are a
  Production enhancement.

## Alternatives considered
- **Hard delete on request** — violates medical-record retention law. Rejected.
- **In-place clinical edits without history** — medico-legally unacceptable. Rejected.

## Trade-offs
Soft delete + versioning grow the tables and require queries to filter `deleted_at`; retention values are
pending legal input (parameters, not architecture). Consistent with crypto-shred (DDR 0006) for true
erasure once windows expire.

## Consequences
The schema honors erasure to the maximum the law allows without breaching retention, and preserves an
amendment trail. Legal durations plug into `retention_*` with no re-architecture.
