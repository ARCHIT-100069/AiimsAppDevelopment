# DDR 0004 — Bounded-context Postgres schemas

**Status:** Accepted · **Date:** 2026-07-04 · **Confidence:** Med-High · **Implements:** Blueprint §7

## Context
The monolith is organized into bounded contexts (blueprint §7). The database can either mirror those
boundaries or use one flat schema.

## Decision
Use domain-oriented Postgres schemas: `platform`, `clinical`, `orders`, `billing`, `consent`, `audit`,
`reference`. RLS remains per-table regardless of schema.

## Alternatives considered
- **Single flat schema with table-name prefixes** — simplest for tooling, but boundaries are only a naming
  convention with no enforcement. Rejected for clarity/ownership.
- **Database-per-context** — over-fragments a system that must join across contexts transactionally.
  Rejected.

## Trade-offs
Multi-schema adds minor Drizzle config and `search_path`/grant overhead. Accepted in exchange for visible
module boundaries and clean per-schema grants that mirror code ownership.

## Consequences
Schema = context boundary in the DB; grants and future service-extraction (ADR 0001) align to these seams.
