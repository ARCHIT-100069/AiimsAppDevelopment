# DDR 0003 — Least-privilege Postgres role model

**Status:** Accepted · **Date:** 2026-07-04 · **Confidence:** High · **Implements:** ADR 0002

## Context
`FORCE ROW LEVEL SECURITY` is only meaningful if the application connects as a role that cannot bypass it.
Table owners and `BYPASSRLS`/superuser roles skip RLS.

## Decision
Four roles with separated duties:
- **`aiims_owner`** — owns objects; used only by migrations.
- **`aiims_migrator`** — runs DDL / RLS / partition migrations in CI.
- **`aiims_app`** — application runtime; **not** owner, **not** superuser, **no `BYPASSRLS`** → RLS always
  applies.
- **`aiims_readonly`** — analytics/replica reads; RLS enforced.

## Alternatives considered
- **Single app role that owns tables** — owner bypasses RLS unless FORCE + care; brittle. Rejected.
- **Superuser/BYPASSRLS for the app** — defeats the entire isolation model. Rejected.

## Trade-offs
More roles and grant management, and migrations need an explicit tenant-bypass context. Worth it: it makes
cross-tenant leakage impossible from the app tier even with buggy SQL.

## Consequences
The app's blast radius is bounded by RLS at all times. Grants are least-privilege per schema; the isolation
CI gate runs under `aiims_app` to exercise production-equivalent enforcement.
