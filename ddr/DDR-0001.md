# DDR 0001 — UUIDv7, application-generated primary keys

**Status:** Accepted · **Date:** 2026-07-04 · **Confidence:** High · **Implements:** ADR 0002/0011

## Context
Every table needs a primary-key strategy that is index-friendly, non-enumerable, safe under the
dedicated-DB promotion path (ADR 0002), and available before insert (the outbox correlates an event id
with the business row in one transaction).

## Decision
Use `uuid` primary keys generated as **UUIDv7 in the application layer**. Adopt Postgres-native
`uuidv7()` only once Aurora GAs PostgreSQL 18.

## Alternatives considered
- **`bigserial`/identity** — leaks row counts, and collides when merging/promoting tenants to dedicated
  databases. Rejected.
- **UUIDv4** — random, causes B-tree index fragmentation and poor cache locality at scale. Rejected.
- **Native `uuidv7()` now** — ideal, but Aurora lags upstream; depending on it would block us. Deferred.

## Trade-offs
UUIDs are 16 bytes vs 8 for bigint (larger indexes), but UUIDv7's time-ordering recovers most of the
insert/locality performance, and the operational/security benefits dominate for a multi-tenant PHI system.

## Consequences
IDs are opaque, sortable by creation time, and portable across shared/dedicated deployments. Generation
lives in `packages/db`; a single helper is the only source of ids.
