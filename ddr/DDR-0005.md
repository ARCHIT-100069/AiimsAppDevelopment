# DDR 0005 — FHIR-regenerable hybrid modeling (columns + `fhir_extensions`)

**Status:** Accepted · **Date:** 2026-07-04 · **Confidence:** High · **Implements:** ADR 0003

## Context
Clinical tables must be fast for OLTP yet able to regenerate valid FHIR R4 (India-profile) resources on
demand (ADR 0003). FHIR resources are deeply nested and irregular.

## Decision
Hybrid per clinical table:
- **Promote hot fields to typed columns** (queried/indexed/validated) — the operational model.
- **`fhir_extensions jsonb`** holds any FHIR-required field not promoted, so fidelity is never lost.
- **Stable `fhir_id` + `identifiers jsonb`** (ABHA, MRN, council reg) for round-tripping.
- A mapping layer regenerates bundles; the DB is never the FHIR store.

## Alternatives considered
- **FHIR-native storage (JSONB documents / HAPI JPA)** — kills query performance and indexing for OLTP.
  Rejected as system of record.
- **Fully normalized to every FHIR element** — explodes table count and slows writes. Rejected.

## Trade-offs
Requires a mapping layer and conformance testing, and discipline about what is promoted vs JSONB. In
exchange: fast internal system + compliant external sharing, insulated from FHIR version churn.

## Consequences
Any required India-profile field must be at least representable in `fhir_extensions`. A field audit
(DATABASE-ARCHITECTURE §19.1) precedes finalizing promoted columns.
