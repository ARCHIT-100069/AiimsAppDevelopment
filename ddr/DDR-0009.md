# DDR 0009 — Optimistic concurrency + slot exclusion constraint

**Status:** Accepted · **Date:** 2026-07-04 · **Confidence:** High · **Implements:** Blueprint §26

## Context
Concurrent edits to clinical/scheduling aggregates must not silently overwrite each other, and appointment
slots must not double-book.

## Decision
- **Optimistic concurrency:** `version int` on mutable aggregates; updates use `WHERE id = ? AND
  version = ?` and bump `version`; a 0-row update ⇒ `409 Conflict`.
- **Double-booking guard:** an exclusion constraint on `(tenant_id, practitioner_id,
  tstzrange(start_at, end_at))` using `btree_gist`.
- Default isolation `READ COMMITTED`; `SERIALIZABLE` only where an invariant demands it.

## Alternatives considered
- **Pessimistic locking (`SELECT … FOR UPDATE`) everywhere** — hurts throughput and risks lock contention
  in a 24/7 system. Reserved for narrow cases.
- **App-layer overlap checks** — race-prone under concurrency. Rejected for slots in favor of a DB
  constraint.

## Trade-offs
Optimistic concurrency surfaces conflicts to the client (must handle 409). The exclusion constraint needs
the `btree_gist` extension. Both are standard and low-cost.

## Consequences
Lost-update and double-booking are prevented at the database. Callers implement retry-on-conflict.
