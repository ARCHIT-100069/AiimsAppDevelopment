# DDR 0011 — Migration governance: RLS/roles as reviewed SQL, drizzle-kit RLS management disabled

**Status:** Accepted · **Date:** 2026-07-04 · **Confidence:** High · **Implements:** ADR 0011

## Context
Drizzle was chosen partly for native RLS (ADR 0011), but `drizzle-kit` can **silently drop RLS policies**
if it "manages" them — a catastrophic footgun for a PHI system.

## Decision
- **Table/column migrations:** generated by `drizzle-kit`.
- **RLS policies, roles, GRANT/REVOKE, `FORCE RLS`, partitions:** **hand-written, reviewed SQL
  migrations.** `drizzle-kit` is configured to **not** manage roles/RLS.
- A **CI policy-diff check fails the build on any unexpected RLS policy removal.**
- Migrations run as `aiims_migrator`; **expand/contract** pattern for zero-downtime (24/7 hospitals);
  forward-only in prod with a documented rollback plan.

## Alternatives considered
- **Let drizzle-kit manage RLS** — exposes the silent-drop footgun. Rejected.
- **All migrations hand-written** — loses Drizzle's table-migration productivity. Rejected.

## Trade-offs
Two migration styles (generated tables + hand-written security) to coordinate. Accepted: security-critical
DDL must be explicit and reviewed, not auto-generated.

## Consequences
RLS changes are always intentional and visible. Combined with the isolation CI gate (DDR 0002 /
DATABASE-ARCHITECTURE §17), a policy regression cannot reach production.
