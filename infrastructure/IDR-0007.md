# IDR-0007 — ElastiCache Redis deployment

**Status:** Accepted · **Version:** 1.0 · **Owner:** Cloud & Infra Architect · **Date:** 2026-07-04

## Context
Redis backs caching, rate limiting, and BullMQ queues (Backend §15); it must be HA and encrypted, and it
is not a system of record.

## Decision
**ElastiCache for Redis, Multi-AZ** with automatic failover; **encryption in transit + at rest (KMS)**;
AUTH enabled; private subnets. Treated as **reproducible** (cache/queue), not a backup source of truth.

## Alternatives Considered
- **Self-managed Redis** — ops burden. Rejected.
- **Single-node** — no failover. Rejected.
- **In-memory only (no Redis)** — loses shared cache/queue across tasks. Rejected.

## Trade-offs
Managed Redis costs more than self-hosted; removes ops and adds HA.

## Consequences
Reliable cache/queue/rate-limit backbone; failure is recoverable without data-of-record loss.
