# IDR-0010 — KMS CMK hierarchy + Secrets Manager

**Status:** Accepted · **Version:** 1.0 · **Owner:** Cloud & Infra Architect · **Date:** 2026-07-04

## Context
Encryption keys and secrets must follow the Security Blueprint (SDR-0005/0006): blast-radius isolation,
rotation, no standing human access to the PHI CMK, no secrets in artifacts.

## Decision
**KMS CMK hierarchy** — separate CMKs for DB storage, S3, secrets, and **PHI field-data keys** (envelope
encryption per DDR 0006); automatic rotation; least-privilege key policies; **no standing human access** to
the prod PHI CMK; **per-tenant CMK** option for dedicated tenants (Production). **AWS Secrets Manager** for
all runtime secrets, injected via task roles, rotation enabled; nothing sensitive in images/repo.

## Alternatives Considered
- **Single CMK** — one compromise/rotation affects everything. Rejected (hierarchy).
- **Secrets in env/SSM plaintext** — weaker. Rejected.
- **Self-managed HSM now** — ops burden; KMS suffices with a CloudHSM path later.

## Trade-offs
Multiple CMKs + rotation add key management; deliver isolation and crypto-shred capability.

## Consequences
Realizes SDR-0005/0006 in infra; per-record/tenant crypto-shred feasible.

## Dependencies
SDR-0005/0006, DDR 0006, IDR-0006/0008.

## Confidence
High. ## Reversibility Low.

## Phase Classification
Structural Foundation + Production (per-tenant CMK).
