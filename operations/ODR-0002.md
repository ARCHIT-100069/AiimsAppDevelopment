# ODR-0002 — SLOs, SLIs & error budgets

**Status:** Accepted · **Version:** 1.0 · **Owner:** SRE/Ops Lead · **Date:** 2026-07-04

## Context
Reliability must be measurable and drive decisions; without SLOs, "reliable enough" is subjective and
velocity/stability trade-offs are ad hoc.

## Decision
Define **SLIs** from PHI-free telemetry (availability, latency, error, saturation, job success, replica lag,
audit-integrity, AI guardrail status) and **SLOs** per user-facing service (MVP proposals: API 99.9%, p95
< 300 ms read / < 800 ms write, OPD flow ≥ 99.5%, RPO ≤ 5 min). **Error budget = 1 − SLO** governs change
velocity: healthy → ship; exhausted → freeze risky changes and stabilize. Fast/slow burn alerts page on-call.

## Alternatives Considered
- **Uptime-only monitoring** — misses latency/correctness/UX. Rejected (multi-SLI).
- **No error-budget policy** — endless feature push erodes reliability. Rejected.

## Trade-offs
Defining/maintaining SLOs takes effort and honest targets; enables objective, data-driven ops.

## Consequences
Measurable reliability; principled velocity/stability balance; actionable alerts.
