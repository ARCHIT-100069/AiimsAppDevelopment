# BDR-0009 — Layered validation strategy

**Status:** Accepted · **Version:** 1.0 · **Owner:** Principal Engineer · **Date:** 2026-07-04

## Context
For a clinical system, input correctness and invariant enforcement are safety and integrity concerns; a
single validation point is insufficient.

## Decision
Three layers: (1) **Edge/API** Zod validation from `api-contracts` (shape/type/range; shared with frontend);
(2) **Domain** aggregates enforce **business invariants** (authoritative, caller-independent); (3) **DB**
constraints (NOT NULL/FK/CHECK/unique/exclusion) as the final backstop (DDR 0008/0009). Coded values checked
against `reference` code systems (DDR 0012).

## Alternatives Considered
- **Edge validation only** — bypassable by other callers; misses invariants. Rejected.
- **DB constraints only** — poor UX, coarse errors. Rejected as sole layer.

## Trade-offs
Some duplication across layers; buys defense-in-depth and safe failure.

## Consequences
Bad data is rejected early and cannot violate invariants regardless of entry path.
