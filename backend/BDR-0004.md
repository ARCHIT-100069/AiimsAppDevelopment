# BDR-0004 — Transaction boundary = application service (UoW + tenant context + outbox)

**Status:** Accepted · **Version:** 1.0 · **Owner:** Principal Engineer · **Date:** 2026-07-04

## Context
Tenant isolation (RLS), audit, and event delivery all depend on a correct, single transaction per use-case
with the tenant/actor context set (DDR 0002/0007).

## Decision
The **application service is the transaction boundary** (unit of work). At tx start it sets
`SET LOCAL app.tenant_id`/`app.actor_id` from the verified token. Business write **+ outbox event +**
audit commit **atomically**. No external/dual writes inside the tx. Optimistic concurrency (`version`)
guards mutable aggregates (DDR 0009).

## Alternatives Considered
- **Transactions in repositories** — fragments the unit of work; multiple partial commits. Rejected.
- **Ambient/implicit transactions** — hidden control flow; hard to reason about. Rejected.
- **Publish to broker inside tx** — dual-write problem; outbox chosen instead (DDR 0007).

## Trade-offs
Application services must own tx orchestration; buys atomic correctness for isolation/audit/events.

## Consequences
One tenant per tx; no lost/orphan events; audit atomic with change.

## Dependencies
DDR 0002/0007/0009, SDR-0003, BDR-0005.

High. ## Reversibility Low.
