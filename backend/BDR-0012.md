# BDR-0012 — Cross-cutting middleware order & observability

**Status:** Accepted · **Version:** 1.0 · **Owner:** Principal Engineer · **Date:** 2026-07-04

## Context
Security and observability must be enforced uniformly and in the correct order — authorization before
handling, tenant context before any DB access, audit after commit.

## Decision
Fixed NestJS pipeline: **AuthN → Tenant-context (tx + SET LOCAL) → AuthZ (PDP) → Validation (Zod) →
Controller → Application service → Commit → Audit emit (outbox) → Response mapper**, with a **global
exception filter** on error. **OpenTelemetry** traces/metrics + **structured JSON logs** (correlation +
tenant + actor, **no PHI**, SDR-0010). Health/readiness probes and security signals (authz denials,
isolation anomalies, audit-integrity failures) are first-class.

## Alternatives Considered
- **Per-handler cross-cutting logic** — inconsistent order, easy to forget (e.g. tenant context). Rejected.
- **Wrong ordering (authz after handler)** — security holes. Rejected.

## Trade-offs
A fixed global pipeline is less flexible per-endpoint; that rigidity is the safety guarantee.

## Consequences
Every request is authenticated, tenant-scoped, authorized, validated, and audited — no opt-out; consistent
telemetry without PHI.
