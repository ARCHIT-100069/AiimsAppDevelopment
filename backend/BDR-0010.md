# BDR-0010 — Error taxonomy & response envelope

**Status:** Accepted · **Version:** 1.0 · **Owner:** Principal Engineer · **Date:** 2026-07-04

## Context
Consistent, safe error handling is required for API usability and to avoid leaking PHI/secrets/stack traces
(SDR-0009/0010).

## Decision
Typed error taxonomy: `DomainError`, `ApplicationError` (authz/not-found/conflict), `IntegrationError`,
`InfrastructureError`. A **global exception filter** maps errors → a stable **response envelope** with an
error code; **no PHI/secret/stack** in responses; 5xx logged with a correlation id only. Standard mappings:
409 conflict, 422 validation, 403 authz, 404 not-found; integration/AI/notification failures degrade
gracefully (off the critical path).

## Alternatives Considered
- **Ad hoc try/catch per handler** — inconsistent, leak-prone. Rejected.
- **Raw framework errors to clients** — leaks internals/PHI. Rejected.

## Trade-offs
Requires an error-mapping discipline; delivers consistent, safe, debuggable errors.

## Consequences
Uniform client contract; no sensitive leakage; graceful degradation.

## Dependencies
