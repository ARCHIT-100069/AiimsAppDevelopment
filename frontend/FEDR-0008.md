# FEDR-0008 — Authorization-aware UI (server-authoritative)

**Status:** Accepted · **Version:** 1.0 · **Owner:** Frontend Lead · **Date:** 2026-07-04

## Context
The UI should present only permitted actions, but client-side authorization must never be a security
control (SDR-0002).

## Decision
**Capability-driven rendering:** show/enable actions from the user's roles/permissions (token claims +
capabilities endpoint); navigation/buttons/fields adapt. **Client authz is UX only** — the server PEP/PDP
is authoritative; every action is server-enforced and audited. Break-glass/elevated flows present explicit,
audited confirmation UX (Production).

## Alternatives Considered
- **Client-enforced authorization** — trivially bypassable; a security hole. Rejected.
- **Show-everything, fail-on-submit** — poor UX, leaks capability info. Rejected.

## Trade-offs
Capability metadata must be delivered/maintained; yields good UX without weakening security.

## Consequences
Clean, role-appropriate UI; security remains server-side.

## Dependencies
SDR-0002, APDR-0004, FEDR-0009.
