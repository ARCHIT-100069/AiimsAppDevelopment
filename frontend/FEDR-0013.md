# FEDR-0013 — Frontend security & PHI-on-client policy

**Status:** Accepted · **Version:** 1.0 · **Owner:** Frontend Lead · **Date:** 2026-07-04

## Context
Clients handle PHI and tokens; they must not become the weak link (SDR-0001/0004/0009/0010).

## Decision
- **Tokens:** web in httpOnly cookies (never JS-accessible); mobile in OS secure storage only.
- **PHI on client:** none unencrypted at rest; web session-only, mobile encrypted store; cleared on
  logout/tenant-switch; screenshot/backgrounding protection + optional biometric lock (mobile, Production).
- **Transport:** TLS only; **certificate pinning** (mobile, Production). Web **CSP**, XSS-safe rendering,
  SameSite cookies, CSRF protection on the BFF.
- **Least data:** fetch only what a screen needs; **no PHI in client logs/telemetry**; client authz is UX-only.

## Alternatives Considered
- **Convenience caching of PHI in plaintext** — breach risk on device/browser. Rejected (SDR-0004).
- **Trusting client-side authorization** — bypassable. Rejected (SDR-0002).

## Trade-offs
Security constraints add UX/engineering effort (secure storage, CSP, pinning); required for PHI.

## Consequences
Client is a hardened, minimal-exposure surface aligned with the Security Blueprint.

## Dependencies
SDR-0001/0002/0004/0009/0010, FEDR-0007/0010.

High. ## Reversibility Low.
