# FEDR-0010 — Offline-first & encrypted client caching (phased)

**Status:** Accepted (offline PHI pending Security sign-off) · **Version:** 1.0 · **Owner:** Frontend Lead
**Date:** 2026-07-04

## Context
Hospital connectivity is intermittent; clients benefit from offline resilience. But PHI on a device is a
real risk surface (SDR-0004), so this must be phased and security-reviewed.

## Decision
- **Read resilience (MVP-structural):** TanStack Query persistence; **mobile uses an encrypted local store**
  (SQLite/MMKV with OS-key encryption) — **no plaintext PHI at rest**.
- **Write queueing (phased):** offline unsafe writes queued with their **`Idempotency-Key`**, replayed on
  reconnect; conflicts resolve via **409/optimistic concurrency** UX (APDR-0006, DDR 0009).
- **Full offline clinical workflows are Production** and **gated on Security-phase sign-off** of the
  device-storage posture (encryption, remote wipe, screenshot/backgrounding protection).

## Alternatives Considered
- **No offline** — poor field UX. Rejected as end-state, acceptable for earliest MVP.
- **Unencrypted offline PHI** — unacceptable (SDR-0004). Rejected.
- **Client-authoritative conflict merge of PHI** — unsafe. Rejected (server via 409).

## Trade-offs
Offline sync + encryption + conflict UX is complex; phased to avoid premature risk.

## Consequences
Resilience to connectivity gaps without compromising PHI; clear path to full offline in Production.

## Dependencies
SDR-0004, APDR-0006, DDR 0009, FEDR-0005.

## Confidence
Medium. ## Reversibility Medium.

## Phase Classification
Structural Foundation (read cache) + Production Implementation (full offline PHI, gated).
